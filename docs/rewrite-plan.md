# Перенос интернет-магазина с Django на ASP.NET Core

Работа идёт в ветке `csharp-rewrite`. Django-код лежит рядом без изменений, пока новая версия
не догонит его по функциям: с ним сверяемся при переносе каждой части. Ветка `master` не тронута.

Стек новой версии: ASP.NET Core MVC и Razor Pages, EF Core, SQLite, ASP.NET Core Identity, .NET 10.

```
OnlineShop.sln
src/OnlineShop.Web/        приложение
  Models/                  сущности (товары, заказы, адреса и т. д.)
  Data/ShopDbContext.cs    схема базы и правила сохранения
  Data/QueryExtensions.cs  порядок вывода по умолчанию, баннеры «сейчас на сайте»
  Data/Migrations/         миграции EF Core
  Data/DemoData.cs         выдуманный каталог для просмотра витрины
  Infrastructure/          ярлыки, формат цен и дат, сообщения, адреса страниц
  Services/                корзина, фильтры и сортировка каталога, данные шапки и подвала
  Controllers/, Views/     страницы витрины и заказов (MVC)
  Pages/Accounts/          вход, регистрация, профиль, адреса доставки (Razor Pages)
  Pages/Admin/             панель управления /admin (Razor Pages, только для роли «Менеджер»)
  Services/Import/         разбор выгрузок 1С и запись в базу
  Cli.cs                   консольные команды: демо-данные, выдача доступа, импорт из 1С
  wwwroot/                 CSS, JS и заглушка фото (перенесены из static/)
tests/OnlineShop.Tests/    тесты моделей, базы, запросов каталога и страниц целиком
docs/rewrite-plan.md       этот файл
```

Запуск и проверка:

```bash
dotnet test OnlineShop.sln
dotnet run --project src/OnlineShop.Web --urls http://localhost:5080
```

Демо-каталог для просмотра витрины (только в пустую базу, товары, цены и адреса выдуманные):

```bash
dotnet run --project src/OnlineShop.Web -- --seed-demo
```

Доступ в панель управления (аналог `createsuperuser`): зарегистрироваться на сайте, затем

```bash
dotnet run --project src/OnlineShop.Web -- --make-manager <логин>
```

Загрузка из 1С из консоли (аналог `manage.py import_1c`), сначала с `--dry-run`:

```bash
dotnet run --project src/OnlineShop.Web -- --import-1c --price-list "прайс лист.xlsx" --stock "остатки.xlsx" --dry-run
```

База создаётся сама при первом запуске в `src/OnlineShop.Web/App_Data/shop.db`, папка в `.gitignore`.
Новая миграция после правки моделей: `dotnet ef migrations add <Имя> --project src/OnlineShop.Web --output-dir Data/Migrations`
(инструмент `dotnet-ef` прописан в `dotnet-tools.json`, перед первым использованием `dotnet tool restore`).

## Решения по моделям и отличия от Django-версии

1. **Цены в SQLite хранятся целым числом тиынов, объём целым числом тысячных.** SQLite хранит
   `decimal` строкой и не умеет сравнивать и сортировать такие значения, а каталогу нужны сортировка
   по цене и фильтр «цена от и до». Целые числа сравниваются правильно и без потери точности
   (15 990,99 ₸ лежит как 1599099). В C# свойства остаются `decimal`. На PostgreSQL этот перевод
   отключается сам, там будут обычные `numeric(12,2)` и `numeric(10,3)`.
2. **Ярлык товара уникален.** В Django ярлык товара не был уникальным: два товара с одинаковым
   названием получали один ярлык, и страница `/product/{ярлык}/` падала с ошибкой
   MultipleObjectsReturned. Теперь повтор получает суффикс `-2`, `-3`. Так же сделано для категорий
   внутри одного бренда. Ярлык по-прежнему строится по правилам Django и сохраняет кириллицу,
   поэтому адреса страниц не меняются. Если в названии нет ни букв, ни цифр, ярлык будет `product`,
   `category` или `brand`.
3. **Поле `order` называется `SortOrder`.** В C# имя `Order` совпало бы с классом заказа.
4. **Порядок вывода задаётся явно.** В EF Core нет аналога `Meta.ordering`, поэтому запросы
   вызывают методы `Ordered()` из `Data/QueryExtensions.cs`, порядок в них тот же, что был в Django.
5. **Пользователи на ASP.NET Core Identity.** Вместо флага `is_staff` используется роль `Manager`,
   она создаётся первой миграцией. Хеши паролей Django в Identity не подходят: при переносе данных
   (этап 5) покупателям придётся задать пароль заново, либо нужно будет дописать проверку старого хеша.
6. **Координаты хранятся как `double`.** В Django было `Decimal(9,6)`, точности `double` хватает
   с большим запасом, а для карты это естественный тип.
7. **Картинки хранятся путём к файлу** (`ImagePath`), как и в Django. Длина поля увеличена со 100
   до 255 символов, чтобы не упираться в длинные имена файлов.
8. **Даты хранятся в UTC.** Дата создания и изменения товара и заказа ставится при сохранении, как
   `auto_now_add` и `auto_now` в Django.
9. **Часы работы по умолчанию записаны как «Пн-Сб, 9:00-18:00»** через дефис вместо короткого тире.
10. **Схема базы обновляется при запуске приложения**, вручную применять миграции не нужно.

## Отличия витрины от Django-версии (этап 2)

1. **Фильтр по цене проверяет обе границы на одной видимой фасовке.** В Django условия
   накладывались по отдельности, и товар с фасовками за 500 и 5000 ₸ проходил фильтр «от 1000
   до 2000». Скрытые фасовки в фильтре, сортировке и блоке «Есть в наличии» больше не учитываются.
2. **Товары без цены при сортировке по цене всегда в конце.** В Django «сначала дешевле»
   начиналось с позиций «цена уточняется», хотя комментарий в коде обещал обратное.
3. **Поиск не зависит от регистра и для кириллицы.** Встроенные `LIKE` и `lower()` в SQLite
   понимают регистр только у латиницы, поэтому в Django «гель» не находил «Гель». Теперь в SQLite
   добавлена своя функция `ulower` (`Infrastructure/SqliteFunctions.cs`).
4. **Скрытый бренд прячет свои категории** на главной, в каталоге в шапке и в фильтре поиска.
   В Django плитки и страницы категорий скрытого бренда оставались доступны.
5. **Корзина.** Положить можно только видимую фасовку с ценой. Если фасовку потом скрыли или убрали
   ей цену, она тихо выпадает из корзины. После добавления сайт возвращает только на свои страницы:
   в Django адрес возврата `next` можно было подменить на чужой сайт.
6. **Корзина хранится в памяти сервера** и сбрасывается при его перезапуске. В Django сессии лежали
   в базе. Для разработки этого достаточно, перед запуском в работу сессии надо перенести в базу.
7. **Формат и тексты.** Цены с разделителем разрядов («15 990 ₸»), склонение на плитках
   («1 товар», «3 товара»). В заголовках вкладок «Корзина | GRASS Актау» вместо длинного тире,
   пустая фасовка подписана «не указана» вместо прочерка. Поля формы заказа оформлены в стиле сайта,
   в Django они выводились без стилей. В фильтре поиска у категории подписан бренд, потому что
   у разных брендов бывают категории с одинаковым названием. Поля цены в фильтре текстовые
   с цифровой клавиатурой, чтобы принимать запятую.
8. **Адреса страниц без косой черты в конце** (`/catalog/grass/автошампуни` вместо
   `/catalog/grass/автошампуни/`). Сайт ещё нигде не опубликован, ломать нечего.
9. **Своя страница 404** вместо отладочной страницы Django.

## Отличия личного кабинета от Django-версии (этап 3)

1. **Логин не зависит от регистра.** Identity сравнивает логины без учёта регистра, поэтому
   «Ivan» и «ivan» теперь один и тот же покупатель, а войти можно в любом регистре. В Django это
   были бы два разных логина. Кириллица в логине разрешена, как и раньше.
2. **Проверки пароля.** Длина не меньше 8, не только цифры, не похож на логин, имя, фамилию
   и почту: как в Django. Список распространённых паролей короче: около 60 самых частых вместо
   20 000 у Django, плюс русские раскладочные вроде «йцукен». Похожесть считается через общую
   подпоследовательность, это близко к `difflib`, которым пользуется Django, но не совпадает
   до знака.
3. **Сообщение при неудачном входе короче:** «Неверный логин или пароль.»
4. **После входа возврат по параметру `ReturnUrl`** (так принято в ASP.NET Core) вместо `next`,
   и только на страницы своего сайта.
5. **Удаление адреса только кнопкой с подтверждением** (POST-запросом). Отдельного адреса
   `/accounts/profile/addresses/5/delete` больше нет: в Django он по GET просто перенаправлял
   к списку.
6. **Страницы кабинета сделаны на Razor Pages**, а история и страница заказа остались
   в MVC-контроллере `OrdersController` рядом с оформлением заказа.
7. **Ключи шифрования куки входа** ASP.NET Core хранит сам в профиле пользователя Windows
   (`%LOCALAPPDATA%\ASP.NET\DataProtection-Keys`), в репозиторий они не попадают. На сервере
   их надо будет положить в постоянную папку, иначе после переустановки все выйдут из аккаунтов.

Как и в Django, вход запоминается на две недели, при выходе очищается корзина, почта
необязательна и может повторяться у разных покупателей, ключ Google Maps задаётся переменной
окружения `GOOGLE_MAPS_API_KEY`, без неё на форме адреса открытые карты OpenStreetMap.

## Отличия панели управления от Django-версии (этап 4)

1. **Панель своя, а не готовая админка.** В ASP.NET Core нет аналога Django admin, поэтому разделы
   сделаны страницами Razor Pages с теми же списками, фильтрами, поиском и правкой прямо в таблице.
   Добавлен раздел «Покупатели и доступ»: в Django его роль играл встроенный раздел «Пользователи»,
   в список функций он сначала не попал.
2. **Доступ через роль «Менеджер».** Первого менеджера назначает команда `--make-manager <логин>`
   (в Django это делал `createsuperuser`), дальше менеджеры выдают доступ друг другу в панели.
   Снять доступ с самого себя нельзя, чтобы панель не осталась без менеджеров.
3. **Сортировка по клику на заголовок** есть в списках товаров, артикулов и заказов, где она
   действительно нужна. В остальных списках порядок постоянный (по очерёдности или по названию).
   В Django сортировался любой столбец.
4. **Нет массового удаления галочками** («Удалить выбранные»). Запись удаляется кнопкой на своей
   странице с подтверждением. Если удалить нельзя (у категории есть товары, артикул заказывали),
   панель прямо говорит почему и что сделать вместо этого.
5. **Заказы.** Можно менять статус, данные доставки, количество и убирать позиции, но не добавлять
   новые: в Django добавление позиции в админке, судя по коду, не работало бы (название и цена
   там только для чтения и остались бы пустыми, а цена в базе обязательна). Заказ не удаляется, для отказа есть статус «Отменён»,
   так история продаж не теряется.
6. **Ярлык, введённый руками,** приводится к тем же правилам, что и автоматический, а пустой
   заполняется из названия кириллицей, как при импорте. В Django-админке скрипт переводил название
   в латиницу (`avtoshampuni`), и ярлыки товаров из админки и из импорта выглядели по-разному.
7. **Цены и количества** в формах принимают и запятую, и точку, и пробелы между разрядами.
8. **Временные файлы импорта** лежат в `App_Data/imports`, а не в раздаваемой сайтом папке `media`:
   иначе прайс с оптовыми ценами можно было бы скачать по ссылке. Имя файла из формы проверяется,
   в Django через него можно было подставить путь к другому файлу на сервере. Брошенные на
   предпросмотре файлы удаляются через сутки. Битый файл или не Excel даёт понятное сообщение
   вместо страницы ошибки.
9. **Фото проверяются по содержимому** (первым байтам файла), а не только по расширению: в Django
   это делал Pillow. Можно загрузить несколько фото товара сразу. Старые файлы удаляются при замене
   и удалении, как делал django-cleanup.
10. **Сроки показа баннера** вводятся по времени Актау.
11. **Родительская категория** должна быть того же бренда и не может быть вложена сама в себя.
    В Django это не проверялось.
12. **На главной панели** видно число новых заказов и видимых фасовок без остатка.
13. **Номер страницы в адресе списков** называется `p`, а не `page`: в Razor Pages имя `page`
    занято под адрес самой страницы.

Разбор выгрузок 1С перенесён один в один, включая мелочи вроде того, что колонка с номером 0
в Python считалась «не найденной» (`find_col(...) or ...`). Проверено тестами на файлах,
собранных по образцу отчётов 1С: настоящих выгрузок в репозитории нет.
